# hgcc 分离编译（RDC 模式）使用介绍 { #hgcc-rdc }

hgcc 的分离编译（separate compilation）由 `-rdc=true` 开启，产物是可重定位设备代码（Relocatable Device Code，下文简称 RDC）。这个选项同时影响两件事：设备符号能否跨编译单元引用，以及设备代码在编译期还是链接期完成优化。前者决定跨文件的设备代码组织能否构建通过，后者决定运行时性能。本文从一组最小复现开始，依次给出 RDC 与非 RDC 的产物差异、支持的跨文件用法、实测性能代价与 `-dlto` 的补偿效果、接入自有构建系统的分步链接方式，以及为依赖 RDC 的文件加编译期检查的方法，最后给出按报错前缀索引的排错手册。

!!! note
    本文后续示例基于 hgcc `2.2.0`、Ubuntu 24.04、主机编译器 `gcc 13.3.0`。

## 1. 为什么需要 RDC { #why-rdc }

hgcc 默认全程序编译（whole-program compilation），要求设备符号的定义与使用位于同一个编译单元。当设备函数需要调用另一编译单元中的设备函数，或访问另一编译单元中的设备变量时，命令行必须指定 `-rdc=true`（编译阶段可简写为 `-dc`，链接阶段仍须写 `-rdc=true`）。

除了跨文件引用，分离编译还提供全程序编译不具备的能力：更灵活的代码组织、在某些情况下更短的编译时间，以及更小的二进制文件。设备代码可以按模块分别编译、分别打包成静态库，再在链接阶段统一解析，这与主机侧 C++ 的常规工程组织方式一致。代价是设备代码链接本身会影响性能，这也是它不作为默认行为的原因——第 5 节给出实测量级与 `-dlto` 的补偿效果。

将设备函数与调用它的 kernel 分别放到两个文件：

```cpp
// a.hg —— 只有一个设备函数
__device__ int add(int a, int b) { return a + b; }
```

```cpp
// b.hg —— kernel 调用另一个文件中的设备函数
#include <stdio.h>

extern __device__ int add(int, int);

__global__ void k(int *out) { *out = add(3, 4); }

int main() {
    int *d = nullptr, h = -1;
    hggcMalloc((void **)&d, sizeof(int));
    k<<<1, 1>>>(d);
    hggcMemcpy(&h, d, sizeof(int), hggcMemcpyDeviceToHost);
    printf("add(3,4)=%d  err=%s\n", h, hggcGetErrorString(hggcGetLastError()));
    hggcFree(d);
    return 0;
}
```

分别编译：

```text
$ hgcc -c a.hg -o a.o                  # 通过
$ hgcc -c b.hg -o b.o                  # 失败
Error : Unimplement _Z3addii
; Function Attrs: convergent nounwind null_pointer_is_valid
declare i32 @_Z3addii(i32, i32) local_unnamed_addr #1
Error : Unimplement
lld: error: undefined symbol: add(int, int)
>>> referenced by /tmp/b-hggc-ppu-llc-ppu001-n4ZMC9.o:(k(int*))
hgcc error: Exited with error code 1
```

失败发生在编译 `b.hg` 阶段，而非链接阶段：非 RDC 模式下每个编译单元都独立完成一次完整的设备链接，`add` 在本编译单元中没有定义，设备链接器直接报 undefined symbol（这一步内嵌在编译过程中，前缀为 `lld:`），因此不会进行到 `hgcc a.o b.o`。报错中混杂的 `Error : Unimplement` 与原始 LLVM IR 片段则属于编译器内部诊断信息意外暴露在用户输出中，第 8 节给出用预定义宏将其替换为自定义错误信息的方法。

## 2. 开启 RDC { #enable-rdc }

开启 `-rdc=true` 后，编译阶段生成可重定位设备代码，链接阶段由 hgcc 统一做设备链接与主机链接。上一节的 `a.hg` / `b.hg` 保持不变，只增加 `-rdc=true`：

```text
$ hgcc -rdc=true -c a.hg -o a.o
$ hgcc -rdc=true -c b.hg -o b.o
$ hgcc -rdc=true a.o b.o -o app
$ ./app
add(3,4)=7  err=no error
```

参与链接的所有含设备代码的目标文件都必须以 `-dc` 或 `-rdc=true` 编译。单文件程序加 `-rdc=true` 同样能正常编译运行，因此对所有 `.hg` 统一开启 RDC 在**功能**上是安全的；性能上则需要同时启用 `-dlto`，见第 5 节。构建系统中最直接的统一启用方式是环境变量，它会作用于每一次 hgcc 调用：

```bash
export HGCC_PREPEND_FLAGS='-rdc=true'
```

若部分文件未开启 RDC，混合链接的后果是：

```text
$ # a.o 用非 RDC 编译，b.o 用 RDC 编译
$ hgcc -rdc=true a_nordc.o b_rdc.o -o app
hglld: error: undefined reference to '_Z3addii'
hglld: error: undefined symbol: add(int, int)
>>> referenced by b.o:(k(int*))
hglld: error: Invalid out buffer
hglink: error: HGVM_ERROR_COMPILATION
hgcc error: Exited with error code 1
```

含设备代码的非 RDC 目标文件不导出设备符号，与之混合链接必然失败。设备链接器在独立链接阶段的前缀是 `hglld:`，在非 RDC 编译内嵌的设备链接中前缀是 `lld:`，主机链接器则是 `/usr/bin/ld:`；根据前缀可以判断失败发生在哪一步，第 7 节的排错手册即按此索引。

## 3. RDC 与非 RDC 的产物差异 { #artifact-diff }

`-rdc=true` 解决了链接问题，也改变了产物形态。同一份源码（一个 kernel 调用一个 `__device__` helper）分别编译为两个 `.o`，从目标文件、设备端二进制、主机侧符号三个角度对比。

### 3.1. ELF 段名与体积 { #elf-sections }

```text
$ hgcc -c t.hg -o t_nordc.o
$ hgcc -rdc=true -c t.hg -o t_rdc.o
$ readelf -S t_nordc.o | grep hggc
  [6] .hggc_fatbin       000398
$ readelf -S t_rdc.o | grep hggc
  [6] .hggc_relfatbin    000388
$ du -h t_nordc.o t_rdc.o
62K     t_nordc.o
126K    t_rdc.o
```

上面 `readelf` 的输出只保留了段号、段名与文件偏移三列。关键变化是 `.hggc_fatbin`（可执行设备代码）换成了 `.hggc_relfatbin`（relocatable），目标文件体积从 62 KB 增加到 126 KB——RDC 版本要同时携带可重定位设备代码和额外元信息。

体积对比还会受 fatbinary 压缩设置影响：hgcc 默认会压缩嵌入应用程序或库二进制中的 fatbinary，`--no-compress` 关闭压缩，`--compress-mode={default|size|speed|balance|none}` 选择压缩策略；对比两种构建方式的产物体积时，应确保两侧的压缩设置一致。

### 3.2. `hgobjdump --list-all`：RDC 保留独立的设备函数 { #list-all }

`hgobjdump` 能列出目标文件中的设备侧内容：

```text
$ hgobjdump --list-all t_nordc.o
ELF FILE 1 (PPU 1.0) (SIMT):
Func 1 (kernel): _Z5kmainPi

$ hgobjdump --list-all t_rdc.o
ELF FILE 1 (PPU 1.0) (SIMT):
Func 1 (device): _Z6helperi
Func 2 (kernel): _Z5kmainPi
```

非 RDC 版本中 `helper()` 已经被内联进 kernel，符号不再存在。RDC 版本必须将它保留为一个独立的 `(device)` 函数，因为其他编译单元可能要调用它。这是第 5 节性能差距的来源。

### 3.3. 设备端产物：EXEC 与 REL { #exec-vs-rel }

```text
$ hgcc -hgbin t.hg -o t_nordc.hgbin
$ hgcc -rdc=true -hgbin t.hg -o t_rdc.hgbin
$ file t_*.hgbin
t_nordc.hgbin: ELF 64-bit LSB executable, ...
t_rdc.hgbin:   ELF 64-bit LSB relocatable, ...
```

`readelf -h` 的结论相同：非 RDC 是 `Type: EXEC (Executable file)`，RDC 是 `Type: REL (Relocatable file)`。RDC 版本带有真正的重定位表，条目直接指向被调用的设备函数：

```text
Relocation section '.rela.hg_info' contains 4 entries:
  Offset             Type              Symbol's Name + Addend
  0000000000000004   unrecognized: 15  _Z6helperi + 0
  000000000000001a   unrecognized: 15  _Z5kmainPi + 0
```

非 RDC 版本则只有一条 debug 相关的重定位。

### 3.4. 主机侧符号的变化 { #host-symbols }

`nm -C` 对比两侧的主机符号（表中 `<hash>` 为本次构建的 fatbinary hash `8HP5X6AD8NUE`）：

| 符号 | 非 RDC | RDC |
| :--- | :--- | :--- |
| `__fatDeviceText` | `d`，本地数据，地址 `0x0` | 不出现 |
| `__fatbinwrap_<hash>` | 不出现 | `D`，全局数据，地址 `0x0` |
| `__hggc_module_dtor()` | `t`，本地函数，地址 `0x2da` | 不出现 |
| `__hggcRegisterFatBinary` | `U`，未定义 | 不出现 |
| `__hggcUnregisterFatBinary` | `U`，未定义 | 不出现 |
| `__hggcRegisterLinkedBinary_<hash>` | 不出现 | `U`，未定义 |

`__hggcRegisterLinkedBinary_<hash>` 只由设备链接步骤提供；第 6.1 节和 7.3 节的报错都源于缺少这一步。

### 3.5. 不受 RDC 影响的部分 { #unaffected }

并非所有环节都随之改变，以下行为保持不变：

- **主机侧代码与主机编译选项**：主机端编译的处理流程、`-Xcompiler` 透传的选项、主机目标文件的常规 ELF 段（`.text` / `.data` / `.rodata` 等）都不受影响。
- **不含跨编译单元设备引用的单文件程序**：无论是否指定 `-rdc=true` 都能正确编译运行，只是产物段名与体积不同。
- **纯主机编译单元**：设备链接器会跳过不包含可重定位设备代码的目标文件，因此静态库中混入的纯主机 `.o` 不会引发设备链接错误（4.4 节有实测验证）。
- **运行时 API 与源码写法**：`hggcMalloc` / `hggcMemcpy` / `<<< >>>` 启动语法、错误检查方式在两种模式下完全一致，上面的 `b.hg` 一行未改。

## 4. RDC 支持的跨文件用法 { #cross-tu-usage }

跨文件调用 `__device__` 函数已在第 2 节演示，下面是其余四类用法。其中跨文件 `__device__` 变量在非 RDC 下静默出错，风险最高，放在最前面讨论。

### 4.1. 跨文件 `__device__` 全局变量：非 RDC 下的静默出错 { #device-global }

在一个编译单元中定义的非 const `__device__` 变量，要在其他编译单元中使用，必须写成 `extern` 声明。而非 RDC 模式下不能用 `extern` 定义具有外部链接的 `__device__`、`__shared__`、`__managed__`、`__constant__` 变量：

```cpp
__device__ int var1;        // OK
extern __device__ int var2; // 非 RDC 模式下只产生警告
extern __shared__ int var3; // OK
```

第三行是这条规则的例外：动态分配的 `extern __shared__` 变量本身不含定义，非 RDC 下同样合法。需要关注的是第二行——它仅产生一条警告，不构成错误。先看 RDC 下的正常用法：

```cpp
// ga.hg
__device__ int g_counter = 100;
```

```cpp
// gb.hg
#include <stdio.h>

extern __device__ int g_counter;

__global__ void bump()           { g_counter += 5; }
__global__ void readback(int *o)  { *o = g_counter; }

int main() {
    int h = -1, *d;
    hggcMalloc((void **)&d, sizeof(int));

    bump<<<1, 1>>>();
    hggcDeviceSynchronize();

    readback<<<1, 1>>>(d);
    hggcMemcpy(&h, d, sizeof(int), hggcMemcpyDeviceToHost);
    printf("via kernel readback: g_counter=%d (expect 105)\n", h);

    int h2 = -1;
    hggcError_t e = hggcMemcpyFromSymbol(&h2, g_counter, sizeof(int), 0,
                                         hggcMemcpyDeviceToHost);
    printf("via hggcMemcpyFromSymbol: g_counter=%d, err=%s\n",
           h2, hggcGetErrorString(e));
    return 0;
}
```

```text
$ hgcc -rdc=true -c ga.hg -o ga.o
$ hgcc -rdc=true -c gb.hg -o gb.o
$ hgcc -rdc=true ga.o gb.o -o gapp
$ ./gapp
via kernel readback: g_counter=105 (expect 105)
via hggcMemcpyFromSymbol: g_counter=105, err=no error
```

初值 100 + 5 = 105，两条读取路径结果一致。`hggcMemcpyFromSymbol` 可以直接传变量名（`hggc_runtime_api.hpp` 提供了接受符号引用的模板重载）。

去掉 `-rdc=true` 后，编译只产生一条警告——

```text
gb.hg:2:1: warning:  extern declaration of the entity 'g_counter' is treated as a static definition
```

链接成功，程序正常运行结束，输出 `via kernel readback: g_counter=5 (expect 105)`。

**这是本文唯一一个静默出错的场景。** 非 RDC 模式下，`extern __device__ int g_counter;` 被降级为当前编译单元的 static 定义，每个编译单元各持一份独立副本：`ga.hg` 中设定的初值 `100` 丢失，`gb.hg` 中的副本从 0 开始，加 5 得 5；程序正常退出、`err=no error`、没有任何运行时报错。

跨文件 `extern __device__` **函数**在非 RDC 下直接报错（第 1 节），问题立即暴露；**变量**只产生一条警告，容易被 `-w` 或大量编译日志掩盖。项目中出现 `extern __device__` 变量时，需要确认 RDC 已经开启，第 8 节给出用宏做编译期检查的方法。

### 4.2. 跨文件 `__constant__` 变量 { #constant-var }

同样的写法适用于 `__constant__`，RDC 下工作正常：

```cpp
// ca.hg
__constant__ int   c_val;
__constant__ float c_arr[4];
```

```cpp
// cb.hg
#include <stdio.h>

extern __constant__ int   c_val;
extern __constant__ float c_arr[4];

__global__ void k(int *o, float *f) {
    o[0] = c_val;
    for (int i = 0; i < 4; ++i) f[i] = c_arr[i];
}

int main() {
    int hv = 1234;  float ha[4] = {1.5f, 2.5f, 3.5f, 4.5f};
    hggcError_t e1 = hggcMemcpyToSymbol(c_val, &hv, sizeof(int));
    hggcError_t e2 = hggcMemcpyToSymbol(c_arr, ha, sizeof(ha));
    /* ... launch, copy back, print ... */
}
```

```text
$ hgcc -rdc=true -c ca.hg -o ca.o
$ hgcc -rdc=true -c cb.hg -o cb.o
$ hgcc -rdc=true ca.o cb.o -o capp
$ ./capp
device saw c_val=1234 (want 1234), c_arr=1.5 2.5 3.5 4.5 (want 1.5 2.5 3.5 4.5)
err=no error
```

非 RDC 下 `__constant__` 在编译 `cb.hg` 时直接报错，不存在静默降级：

```text
lld: error: undefined symbol: c_val
>>> referenced by /tmp/cb-hggc-ppu-llc-ppu001-ElMvHb.o:(k(int*, float*))
lld: error: undefined symbol: c_arr
hgcc error: Exited with error code 1
```

三者对比：

| 跨文件引用的实体 | 非 RDC 下的行为 | 风险等级 |
| :--- | :--- | :--- |
| `extern __device__` 函数 | 编译期报错（`lld: undefined symbol`） | 低，编译期即暴露 |
| `extern __constant__` 变量 | 编译期报错（`lld: undefined symbol`） | 低，编译期即暴露 |
| `extern __device__` 变量 | 仅一条警告，静默降级为 static，结果错误 | **高，静默出错** |

### 4.3. 同名 `static __device__` 函数不会冲突 { #static-device }

设备符号的可见性遵循 C++ 的 `extern` / `static` 规则：`extern` 符号可跨文件引用，`static` 符号只在当前编译单元可见，因此不同文件中可以定义同名的 `static` 设备符号。

```cpp
// sa.hg
static __device__ int helper() { return 11; }
__device__ int fromA() { return helper(); }
```

```cpp
// sb.hg
static __device__ int helper() { return 22; }
__device__ int fromB() { return helper(); }
```

```cpp
// smain.hg
extern __device__ int fromA();
extern __device__ int fromB();
__global__ void ks(int *o) { o[0] = fromA(); o[1] = fromB(); }
```

RDC 构建后运行结果是 `fromA=11  fromB=22`，两个函数各自调用本编译单元内的 `helper()`。

### 4.4. 设备端静态库（`.a`） { #device-static-lib }

设备链接器能读取静态库（`.a`）但会忽略动态库（`.so`），并且会跳过不包含可重定位设备代码的目标文件。下面的示例工程覆盖了这三条行为：

```cpp
// lib_a.hg
__device__ int lib_add(int a, int b) { return a + b; }

// lib_b.hg
__device__ int lib_mul(int a, int b) { return a * b; }

// lib_unused.hg —— 纯主机编译单元，不含任何设备代码
int host_only_helper(int x) { return x - 1; }
```

```cpp
// main.hg
extern __device__ int lib_add(int, int);
extern __device__ int lib_mul(int, int);
extern int host_only_helper(int);

__global__ void k(int *o) { o[0] = lib_add(3, 4); o[1] = lib_mul(6, 7); }
```

**方式一：用 `ar` 构建静态库。**

```text
$ hgcc -rdc=true -c lib_a.hg      -o lib_a.o
$ hgcc -rdc=true -c lib_b.hg      -o lib_b.o
$ hgcc -rdc=true -c lib_unused.hg -o lib_unused.o
$ ar rcs libmydev.a lib_a.o lib_b.o lib_unused.o
$ hgcc -rdc=true main.hg -L. -lmydev -o app_ar
$ ./app_ar
lib_add(3,4)=7  lib_mul(6,7)=42  host_only_helper(10)=9  err=no error
```

纯主机编译单元 `lib_unused.o` 未引发设备链接器报错，其中的主机函数仍然可用（`host_only_helper(10)=9`）——「跳过不含设备代码的目标文件」正是指这种情况。

**方式二：用 `hgcc -lib` 构建静态库。**

```bash
hgcc -rdc=true -lib lib_a.hg lib_b.hg lib_unused.hg -o libmydev2.a
hgcc -rdc=true main.hg -L. -lmydev2 -o app_lib
```

结果与方式一相同。长写法 `--library-path=. --library=mydev` 同样可用。

`.so` 的表现最容易误导排查。将设备代码构建为 `.so`，主机符号表中两个设备符号均存在：

```text
$ hgcc -shared -rdc=true lib_a.o lib_b.o -o libmydev.so
$ nm -DC libmydev.so | grep lib_
000000000000147e T lib_add(int, int)
00000000000015e8 T lib_mul(int, int)
```

但用于链接时：

```text
$ hgcc -rdc=true main.hg ./libmydev.so -o app_so
hglld: error: undefined reference to '_Z7lib_addii'
hglld: error: undefined symbol: lib_add(int, int)
>>> referenced by /tmp/main-9aeUHQ.o:(k(int*))
hglld: error: Invalid out buffer
hglink: error: HGVM_ERROR_COMPILATION
hgcc error: Exited with error code 1
```

这两个符号对主机链接器可见，对设备链接器不可见。直接从源码构建 `.so`，结果相同。**跨库共享设备代码只能用 `.a`**，`.so` 只能承载主机侧符号。

## 5. 性能代价与 `-dlto` { #perf-and-dlto }

第 1 节提到 RDC 不作为默认行为的原因是性能，这里给出实测量级。分离编译之后跨文件优化机会有限，性能低于全程序编译；`-dlto`（链接时优化）把统一优化推迟到链接阶段完成，代价是链接时间变长（本文未测量链接耗时）。

具体差距与场景有关。下面这个场景对 RDC 最不利：循环中高频调用一个极小的设备函数。

```cpp
// f.hg —— 这个函数在变体 (a) 中与 kernel 同一编译单元（可内联），
//          在变体 (b)/(c) 中是独立编译单元（只能发生真实调用）
__device__ float f(float x) { return x * x + 1.0f; }

// kern_body.inc
__global__ void bench(float *out, int iters) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    float x = out[i];
    for (int k = 0; k < iters; ++k) {
        x = f(x) * 0.5f;
        if (x > 1e8f) x = 1.0f;
    }
    out[i] = x;
}
```

三种构建方式：

```bash
# (a) 全程序编译（f 与 kernel 同一个文件）
hgcc -O3 whole.hg -o bench_a

# (b) 分离编译
hgcc -O3 -rdc=true -c f.hg     -o f_b.o
hgcc -O3 -rdc=true -c kmain.hg -o k_b.o
hgcc -O3 -rdc=true f_b.o k_b.o -o bench_b

# (c) 分离编译 + 链接时优化
hgcc -O3 -dc -dlto f.hg     -o f_c.o
hgcc -O3 -dc -dlto kmain.hg -o k_c.o
hgcc -O3 -dlto f_c.o k_c.o  -o bench_c
```

三个变体都显式写了 `-O3`，这与 hgcc 的默认行为一致——hgcc 默认为 PPU 代码使用最高优化级别 `-O3`，基线 (a) 因此已经在最高优化级别上，下文的差距不能归因于优化等级设置。

用 `hggcEventElapsedTime` 计时，数据规模 `N = 256*1024`、迭代次数 `ITERS = 4000`，3 次预热、15 次重复取中位数：

| 构建方式 | kernel 耗时（中位数） | 相对全程序编译 |
| :--- | :--- | :--- |
| (a) 全程序 | 0.2538 ms | 1.00× |
| (b) RDC | 1.2430 ms | **4.90×** |
| (c) RDC + `-dlto` | 0.2537 ms | 1.00× |

三者校验和一致。15 次重复的抖动都在 0.001 ms 量级，差异远超噪声。`-dlto` 一项与全程序编译相差 0.04%。

**4.90× 不是普适结果。** 这是刻意构造的最坏情况：一个只有两条指令的函数，在循环中被调用 4000 次，函数调用开销占绝对主导。真实 kernel 中被分离到独立编译单元的函数通常规模大得多，函数调用开销的占比随之下降；具体降幅取决于函数体规模，本文未做测量。因此该数字衡量的是 RDC 内联损失的上限量级，不应理解为开启 RDC 的普遍性能开销。

### 5.1. 从产物观察内联 { #see-inlining }

性能差距可以从产物直接观察。先看设备端调用图：

```bash
hgcc -rdc=true a.o b.o -o app -Xhglink --dump-callgraph
```

- 变体 (a) 非 RDC：输出为空（非 RDC 不做跨编译单元设备链接，没有 callgraph）；
- 变体 (b) RDC：`bench()` 明确指向 `f()`，两个函数均存在；
- 变体 (c) RDC + `-dlto`：表头之后为空，`f()` 已被 LTO 内联消除。

再看指令级的调用点：

```text
$ hgobjdump --dump-resource-usage=all bench_b
=== bench_b ===
<0x1>  FUNC:_Z1ff          KIND:return             OFFSET:0x30
<0x2>  FUNC:_Z5benchPfi    KIND:direct call        OFFSET:0x168

$ hgobjdump --dump-resource-usage=all bench_c
=== bench_c ===
<0x1>  FUNC:_Z1ff          KIND:return             OFFSET:0x30
<0x2>  FUNC:_Z5benchPfi    KIND:return             OFFSET:0x5f0
```

`bench_b` 的 kernel 中有一条 `KIND:direct call`；`bench_c` 中只剩 `KIND:return`，且 kernel 体积从 `0x168` 增加到 `0x5f0`，循环被展开、函数被内联。

### 5.2. `-dlto` 改变了什么 { #what-dlto-changes }

用 `hgcc --dryrun` 对比 `-dc` 与 `-dc -dlto` 的内部命令，差异集中在三处：

- 设备端 bitcode 版本标记从 `hgrdc_v1` 变为 `hglto_v1`；
- 编译阶段不再执行 `opt` / `llc` / `lld`，而是直接把 LTO 中间表示打包进 fatbinary（未启用 `-dlto` 的 RDC 会打包可重定位设备代码与设备可执行代码两个 image）；
- 链接阶段的设备链接命令增加了 `-lto`。

代码生成整体推迟到了链接期，所以能跨编译单元内联。`--dryrun` 属于调试手段，输出仅用于解释现象，不应写入构建脚本。

### 5.3. `-dlto` 的组合用法 { #dlto-edge-cases }

以下六种组合在 hgcc 2.2.0 上均验证可用：

1. 全部文件 `-dlto`，链接带 `-dlto`；
2. 部分文件 `-dlto`、部分不用，链接带 `-dlto`；
3. 部分文件 `-dlto`，链接不带 `-dlto`；
4. `-dlto` 对象用 `ar` 打包成 `.a` 再链接；
5. `-dlto` 与 `-G`（设备调试信息）共存；
6. 只在编译期加 `-dlto`，或只在链接期加 `-dlto`。

`-dlto` 允许只作用于部分文件：指定该选项的文件参与统一优化，其余文件按常规方式链接。`-dlto` 单独使用即隐含 RDC，不必再指定 `-rdc=true`。

## 6. 分步链接：接入自有构建系统 { #staged-link }

前面几节的链接都由 hgcc 一站式完成。最终链接不由 hgcc 完成时（例如统一使用 `g++` 或 CMake 生成的链接命令），设备链接需要单独执行。

`-dlink`（`--device-link`）单独执行设备链接，输出是一个包含可执行设备代码的主机目标文件，后续仍要交给主机链接器：

```text
$ hgcc -dc a.hg -o a.o
$ hgcc -dc b.hg -o b.o
$ hgcc -dlink a.o b.o -o dlink.o
$ g++ dlink.o a.o b.o \
      -L$PPU_SDK/targets/x86_64-linux/lib \
      -lhggc -lhggcrt1 -lrt -lpthread -ldl \
      -o app2
$ LD_LIBRARY_PATH=$PPU_SDK/targets/x86_64-linux/lib ./app2
add(3,4)=7  err=no error
```

手工链接所需的库就是上面 `g++` 命令中的 `-lhggc -lhggcrt1`。**库名不属于稳定接口**，不建议硬编码；可用 `hgcc --dryrun` 获取当前 SDK 版本的实际链接命令，再据此维护构建脚本中的库列表。

### 6.1. `-nodlink` 的用法 { #nodlink }

`-nodlink`（`--no-device-link`）在链接时跳过设备端链接步骤。单独使用该选项时：

```text
$ hgcc -rdc=true a.o b.o -nodlink -o app_nodlink
/usr/bin/ld: a.o: in function `__hggc_module_ctor()':
a-splitter-S1xQrD.cpp:(.text+0x163): undefined reference to `__hggcRegisterLinkedBinary_22EWOU4JDCFXZ'
collect2: error: ld returned 1 exit status
hgcc error: Exited with error code 1
```

这就是 3.4 节中的符号：每个 RDC 目标文件的 `__hggc_module_ctor()` 都引用 `__hggcRegisterLinkedBinary_<hash>`，而它只由设备链接产生的目标文件提供。`-nodlink` 必须配合 `-dlink` 分两步使用：

```bash
hgcc -rdc=true -dlink a.o b.o -o dlink.o     # 第一步：单独产出设备链接目标文件
hgcc -nodlink dlink.o a.o b.o -o app_2step   # 第二步：主机链接，跳过重复的设备链接
```

缺少第一步时，失败点在主机链接期，而非运行期。

## 7. 排错手册 { #troubleshooting }

按报错前缀索引：`lld:` 出现在编译期，`hglld:` 出现在设备链接期，`/usr/bin/ld:` 出现在主机链接期。

### 7.1. `Error : Unimplement` + `lld: error: undefined symbol` { #err-unimplement }

```text
Error : Unimplement _Z3addii
declare i32 @_Z3addii(i32, i32) local_unnamed_addr #1
lld: error: undefined symbol: add(int, int)
```

- 阶段：编译某个 `.hg` 时（而非链接阶段）
- 原因：该文件引用了其他编译单元的设备符号，但未开启 RDC
- 解决方法：所有 `.hg` 指定 `-rdc=true`（或 `-dc`）
- 预防：见第 8 节的 `#error` 编译期检查

### 7.2. `hglld: error: undefined symbol` + `hglink: error: HGVM_ERROR_COMPILATION` { #err-hglld }

```text
hglld: error: undefined symbol: add(int, int)
>>> referenced by b.o:(k(int*))
hglld: error: Invalid out buffer
hglink: error: HGVM_ERROR_COMPILATION
```

- 阶段：设备链接（前缀 `hglld:`）
- 可能原因：
    1. RDC 与非 RDC 目标文件混合链接（第 2 节）
    2. 各目标文件的目标架构不一致（7.4 节）
    3. 试图从 `.so` 链接设备符号（4.4 节）
- 解决方法：统一 RDC 开关、统一 `-arch`、改用 `.a`

### 7.3. `undefined reference to __hggcRegisterLinkedBinary_<hash>` { #err-register-linked-binary }

```text
/usr/bin/ld: a.o: in function `__hggc_module_ctor()':
undefined reference to `__hggcRegisterLinkedBinary_22EWOU4JDCFXZ'
```

- 阶段：主机链接（前缀 `/usr/bin/ld:`）
- 可能原因：
    1. 使用了 `-nodlink` 但未提供 `-dlink` 产出的目标文件（6.1 节）
    2. 各目标文件 `-arch` 不一致——这个 hash 与架构绑定，所以架构不匹配会在这里暴露（7.4 节）
- 解决方法：补充 `dlink.o`，或统一架构

### 7.4. 架构不一致的 RDC 链接 { #err-arch-mismatch }

共享头文件中的模板函数一旦依赖 `__HGGC_ARCH__`，两个源文件又用不同的 `-arch` 编译，就会出现这类问题：

```text
$ hgcc --gpu-architecture ppu_10 -dc a.hg
$ hgcc --gpu-architecture ppu_15 -dc b.hg
$ hgcc --gpu-architecture ppu_15 a.o b.o
hglld: error: undefined symbol: from_a()
>>> referenced by b.o:(k(int*))
>>> did you mean: from_b()
>>> defined in: b.o

hglld: error: Invalid out buffer
hglink: error: HGVM_ERROR_COMPILATION
hgcc error: Exited with error code 1
```

架构不一致的 RDC 混合链接不会静默通过：要么设备链接器报 `undefined symbol`，要么主机链接器报 `undefined reference to __hggcRegisterLinkedBinary_<hash>`（hash 与架构绑定）。

设备链接要求参与链接的目标文件满足三条兼容性约束：

1. 所有目标文件使用相同的 ABI 版本；
2. 目标 PPU 架构一致；
3. 链接器的 toolkit 版本不低于目标文件的 toolkit 版本。

使用 `-dlto` 时还需满足第四条：LTO 中间表示仅在同一主版本号内兼容，跨主版本混合链接会失败。

实践中架构不一致最常见的来源是多架构构建。HGGC 示例工程默认同时为 ppu001（`--gpu-architecture=ppu_10`）和 ppu0015（`--gpu-architecture=ppu_15`）两种架构构建，如需仅面向某一种架构，应在配置阶段统一设置 `CMAKE_HG_ARCHITECTURES`：

```bash
cmake -DCMAKE_HG_ARCHITECTURES=ppu_10 -B build
```

架构列表应集中在这一处控制，不要在各 target 上分别设置，否则容易出现某个编译单元的 `-arch` 与其余不一致。

共享头文件中不要通过 `__HGGC_ARCH__` 影响跨编译单元共享的实体，详见相关阅读 [hgcc 预定义宏](/blogDetail?bizType=BLOG&id=43) 第 3.2.6 节约束 2。

### 7.5. 寄存器上限沿调用链传播 { #err-reg-limit }

通过 `__launch_bounds__` 或 `--maxrregcount` 限制了寄存器数量的 kernel，其调用的所有函数也必须遵守该限制，否则会产生链接错误。

该问题在全程序编译下较少出现：被调用的设备函数通常与 kernel 在同一编译单元，编译时就已经在同一个寄存器预算内被内联或分配。分离编译之后调用关系要等到设备链接阶段才解析，此时才发现被调用方位于另一个编译单元、按另一套寄存器预算编译。

- 阶段：设备链接
- 原因：kernel 上的寄存器上限约束与其调用链上某个设备函数的实际用量冲突
- 解决方法：放宽 kernel 的 `__launch_bounds__` / `--maxrregcount`；或对被调用方所在的编译单元施加同样的寄存器上限，使整条调用链预算一致
- 相关：`__launch_bounds__` 与 `__HGGC_ARCH__` 配合时的另一类陷阱见相关阅读 [hgcc 预定义宏](/blogDetail?bizType=BLOG&id=43) 第 3.2.5 节

这一条没有附上具体报错文本：诊断内容随调用链结构变化，不宜归纳为单一形式。识别要点是失败发生在设备链接阶段，且诊断指向寄存器或资源约束，而非符号缺失。

## 8. 为依赖 RDC 的文件加编译期检查 { #rdc-guard }

第 1 节那组混杂 `Error : Unimplement` 与原始 LLVM IR 的报错，对不熟悉 RDC 的开发者缺乏定位价值。`__HGGCCC_RDC__` 可以将其替换为自定义错误信息。

`__HGGCCC_RDC__` 在 RDC 模式下编译时被定义，主机端与设备端都定义为 `1`（该宏由命令行 `-D` 注入），未指定 `-rdc=true` 时两端都不定义。`-dlto` 单独使用时也会定义它。任何依赖跨编译单元设备符号的文件顶部可以写：

```cpp
#ifndef __HGGCCC_RDC__
#error "this file references device symbols from other translation units; \
compile with -rdc=true (or -dc)"
#endif

extern __device__ int add(int, int);
// ...
```

忘记开启 RDC 时得到的就是这条自定义错误，而不是编译器内部诊断。对 4.1 节静默出错的场景，这一检查把运行期的错误结果提前为编译期报错。

## 9. 速查表 { #cheatsheet }

**开启 RDC**

```bash
hgcc -rdc=true -c a.hg -o a.o     # 编译（可简写为 -dc）
hgcc -rdc=true a.o b.o -o app     # 链接（此处不能用 -dc）
export HGCC_PREPEND_FLAGS='-rdc=true'   # 构建系统中统一启用
```

**加上链接时优化**（推荐，可消除 RDC 的内联损失）

```bash
hgcc -dc -dlto a.hg -o a.o
hgcc -dlto a.o b.o -o app
```

**分步链接**（接入自有构建系统）

```bash
hgcc -rdc=true -dlink a.o b.o -o dlink.o
hgcc -nodlink dlink.o a.o b.o -o app
# 或用 g++：g++ dlink.o a.o b.o -L$PPU_SDK/targets/x86_64-linux/lib \
#              -lhggc -lhggcrt1 -lrt -lpthread -ldl -o app
```

**设备端静态库**

```bash
hgcc -rdc=true -c lib_*.hg          # 或 hgcc -rdc=true -lib lib_*.hg -o libfoo.a
ar rcs libfoo.a lib_a.o lib_b.o
hgcc -rdc=true main.hg -L. -lfoo -o app     # 只能用 .a，.so 不可用
```

**多架构构建**

```bash
cmake -DCMAKE_HG_ARCHITECTURES=ppu_10 -B build   # 统一控制，避免各 target 架构不一致
```

**观察与诊断**

```bash
hgobjdump --list-all a.o                      # RDC 会额外输出 Func N (device): ...
readelf -h out.hgbin                          # REL = RDC，EXEC = 非 RDC
hgcc -rdc=true a.o b.o -o app -Xhglink --dump-callgraph   # 设备端调用图
hgcc --dryrun ...                             # 查看实际内部命令（仅调试用）
```

**容易出错的三点**

1. 含设备代码的目标文件必须统一启用或统一不启用 RDC，混合链接必然失败。
2. `extern __device__` 变量在非 RDC 下只产生一条警告、随后静默出错，应为这类文件加 `#ifndef __HGGCCC_RDC__ #error ...` 检查。
3. 跨库共享设备代码只能用 `.a`，`.so` 中的设备符号会被设备链接器忽略。

## 10. 总结 { #summary }

RDC 的取舍最终可以收敛为三条建议。

1. 在构建系统中对所有 `.hg` 统一开启 `-rdc=true`，通过 `HGCC_PREPEND_FLAGS` 实施，从根本上消除混合链接这一类错误；单文件程序开启 RDC 在功能上没有副作用。
2. 只要不是单文件工程，就同时启用 `-dlto`：本文实测它把 4.90× 的 kernel 耗时差距缩小到 0.04%，代价只是链接时间变长。
3. 跨库共享设备代码只用 `.a`，并对所有引用跨编译单元设备符号的文件加 `__HGGCCC_RDC__` 检查——4.1 节的 `extern __device__` 变量是本文唯一的静默出错来源，该检查能将其提前为编译期报错。

排查时先看报错前缀：`lld:` 说明失败在编译期，`hglld:` 在设备链接期，`/usr/bin/ld:` 在主机链接期。前缀确定阶段，阶段确定原因范围，第 7 节按此组织。
